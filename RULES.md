# aiva-hud rules

Rules learned the hard way. New rules and verified engine facts go into the matching section, one fact per bullet; say why when the reason is not obvious, and record what the owner rejected so it is not proposed again.

## Workflow

- Checks also run `claude plugin test .` (the `tests/` folder, never synced to live); every listed check must pass before a commit.
- Tests cover only what has broken more than once (a regression test, named in its rule as guarded); any other test is written only after the owner agrees.
- Sync is confirmed once for all: after every finished change whose checks pass and is committed, sync to live without asking. Sync = remove live `hooks/` and `types/`, copy them and `.claude-plugin/plugin.json` from the repo, then `diff -rq --strip-trailing-cr` both trees. Never touch other live files (`CLAUDE.md`, `tsconfig.json`, `.claude-plugin/types/`). Remind the owner to restart the session.
- Install is one line: `/plugin install aiva-hud --marketplace vfesenko94/aiva-hud` (shell: `claude plugin install ...`). The repository root is its own marketplace (`.claude-plugin/marketplace.json`, one entry, `source: "./"`), so it installs what is pushed to `main`. Verified with a local folder source into a throwaway `CLAUDE_CONFIG_DIR`.
- Files the mod writes live under the Claude config folder (`core/folder` `configFolder`: `CLAUDE_CONFIG_DIR`, else `USERPROFILE`/`HOME` + `/.claude`), never derived from `$.plugin.root`: a marketplace install runs from a versioned cache folder that an update replaces.

## Architecture

### Modules and hooks

- `index.ts(x)` is a module's only entry: its strip block, its matcher hooks, re-exports. Modules import only `core`, never each other. A module exports only what another file uses.
- `createX(config)` only when the module owns mutable runtime. `registerX(on, x, isOn)` registers matcher hooks only and returns nothing.
- `$` goes only to named top-level `function` declarations (the validator refuses it via variables, arrays, callbacks, methods): no registries or loops over modules.
- Matcher-less events (`session.*`, `turn.*`, `prompt.*`, `tool.call`, `tool.describe`, ...) may be hooked once per module: all of them live in `register.tsx`.
- Hooks matched to one pane id (`ui.render`, `ui.focus`, `ui.scroll`, `ui.close`, `ui.press`) live beside that pane's code: `context/pane` (`registerPane`, keyboard moves as pure functions in `pane/keyboard.ts`), `model/pane.tsx` (`registerPicker`), `limits/pane.tsx` (`registerLimitsPane`), `settings/pane.tsx` (`registerSettingsPane`). Exception: the Settings `ui.render` lives in `register.tsx`, since its toggle reaches every module through `actions.ts` and `$` cannot be handed to a module as a callback.
- Shared changing session data lives in `core/live` (`Live`: `isWorking`, `turnId`): one `createLive` runtime in the composition root, written only by its hooks there (`turn.start`; `turn.complete`, which also ends aborted turns; `session.start`/`session.end` reset), always on, subagent turns ignored; each change invalidates `ui.render`. Modules take it as `Readonly<Live>` and read it at draw/act time. New shared live data goes there, not into a module's own checks.
- Modules get a plain `isOn()` predicate and never import settings; a module that draws a setting takes a plain getter or value (`registerCache(..., displayOf)`, `registerStrip(on, isHintShown)`, block functions take their `Display`).
- Off means off: hooks pass straight to `next(e)`, no engine calls, drawing or recording; siblings are unaffected.
- Toggle off: flip, release the runtime synchronously, close its pane, persist through `core/writer`, clean up only if still off. Every async commit first checks that its generation/runtime is still current.

### Constants

- Atoms live in the file that uses them. A module's own constants live in its `config.ts` (`pickerConfig`, `settingsConfig`, `contextConfig`, `cacheConfig`, `shellsConfig`, `stripConfig`, `limitsConfig`), imported directly, exported from its `index`, never passed as parameters.
- `core/config.ts` (`baseConfig`, `HudConfig`) keeps only what several modules, `core` or the composition root share, and the plugin options it resolves (cache TTL); a value moves there only when a second reader appears. Pane frame status lives in `core/pane/config.ts` (`paneConfig`), read only by `core/pane`.
- Reusable keyboard labels live in `keyHints` (`core/config.ts`); arrows have no spaces between them: ↑↓←→, ↑↓, ←→.

## UI kit (`core/pane/kit`)

- One file per component, each owning its glyphs and sizes (`buttonSize`, `choiceSize`, `cycleSize`, `checkboxSize`, `paragraphRows`, `tabsShown`, `scrollbarSize`): modules never repeat glyph widths as numbers. Shared parts live in `pressable.ts` and `mark.ts`.
- Controls take no `isFocused`: `selected` inverts, and `paneUi` removes the inverse while the pane is unfocused, so kit controls are drawn only with `pane.ui`. Inverse means focus only, never "active".
- `dim` is a style; `inert` dims and ignores presses but stays a focus stop (picker Apply); `disabled` (cycle, checkbox) draws plain dim Text with no stop.
- `button`: optional `color` (Reset confirm).
- `checkbox` with an empty `label` draws the bare mark with no gap after it, so the selection inverse covers only the mark (Settings Enabled).
- `cycle`: a plain `label: ` beside a pressable face `‹ value ›` (keyed Button, a focus stop). Selected, only the face inverts: arrows in text color, the value with its padding in its `color`. ←/→ change it only while selected, through the `Cell.step` of `settings.navigation` (Settings) or the module's own `ui.scroll` check (picker); the handler checks `stepOf(direction)`, `cycleStep` computes the next value. The value is centered in the widest option so the face keeps its size; `fit` hugs the current value. Narrow: the label is cut first, then dropped. `wrap: false` clamps ←/→ and dims the edge arrow; a press always advances with wrap. Fewer than two options or `disabled`: dim, unpressable.
- `disclosure`: an expandable row head, one keyed plain Button (its `key` is the nav key) holding dim `indent`, the dim `[−]`/`[+]` mark, the label (cut and padded to `labelWidth` with `fill`, optional `bold`/`color`), an optional `value` padded to `valueWidth`, then `tail` parts; `dim` and `hover` pass to the Button. `disclosureMark` is the bare glyph for rows with their own layout (Context turns, steps, calls, summaries: amount column before the mark). Leaves (`isOpen: null`) keep their own Button.
- `meter`: a segmented bar, one run of `cells` glyphs per segment in its `color`, faded with `dim` (`glyph`: `fill` █ by default, `track` ░ for an empty part; `meterGlyphs`), `text` color while `isPointed` or hovered within its `scope`. A segment with `onPress` is a keyed plain Button with the same hover, otherwise plain Text. Returns the segments as an array to sit inline. Never inverse spaces: `paneUi` drops inverse in an unfocused pane, which blanked every bar (fixed; glyphs only turn gray).
- `tabs`: one row, `active` bold, others dim; `selected` passes the module's own focus (Context passes none and keeps the engine ring). A tab with `onPress` is a keyed focus stop, otherwise plain Text (picker `Latest models`). Tabs are separated with a dim ` │ `. Labels cut left to right to `width`; a tab with no room is dropped; `tabsShown` lists the keys that fit, so a module offers stops only for drawn tabs.
- `paragraph`: wrapped text in a fixed-height box clipped to `rows`, optional bold `lead`, returns `{ element, rows }` (null when nothing fits). `paragraphRow` turns it into a stack row asking for its wrapped height.
- `stack`: a column of rows kept by `priority` (lower first) within `room`, in screen order. A row gets at most what is left and is dropped below `minRows` (default `rows`: whole or nothing; `minRows: 1` shrinks). Returns `{ rows, stops, draw }`: fix the selection from `stops` before `draw()`.
- `scrollbar`: a one-column track (`│` dim) with a thumb (`┃`) from `rows`, `total`, `first`; null when everything fits.
- `viewport`: the plugin's own scroll window over a flat list of `Line`s, each exactly one row (`element`, plus its `stops`: the keyed Buttons on it, in tree order). It draws only `rows` lines from `first` in a fixed-height box, one clipped one-row Box per line, with the kit `scrollbar` in a column that is always kept (`viewportWidth`), so rows never reflow when the list starts to overflow. Stops of the lines outside the window stay in the tree as blank Buttons with the same `key` and `onPress`, in two zero-height clipped Boxes pinned to the window's top (before and after the shown lines): the engine's stop list keeps its order and size while the window moves. `viewportFirst` clamps a window, `viewportReveal` moves it the least that shows a `Span` (its head wins when the span is taller than the window), `isInViewport` tells whether a span's head is shown. Text that used to wrap is cut into lines with `wrapText` (`core/format`), since a line can never be two rows.
- `grid`: `gridMove` moves ←/→ to a cell in the same row of a `Cell` grid (`settings.navigation`) when the cell has no `step`.

## Panes

### Placement

- Every pane is designed and checked in both placements; the engine picks one, the plugin cannot. `inline`: a wide, short block above the prompt (main screen at any width, or fullscreen below 110 columns), height from the `rows` request and what the layout spares (seen 11 down to 4). `dock`: a narrow, tall column right of the transcript (fullscreen from 110 columns), width from the `columns` request, 24 to 45% of the terminal. A size the person set wins over both.
- Adapt only from the `ui.render` props (`placement`, `bodyColumns`, `scroll.bodyRows`), read on every draw: no cached sizes, no thresholds of our own.

### Shared pane state

- Every pane module keeps one `PaneState` (`core/pane/state`: `{ isShown, isFocused }`, from `hiddenPane()`) as its `visibility` field and changes it only through the shared helpers: `notePaneState` (from the strip's `$.ui.panes()` read), `hidePaneState`, `showPaneState`, `closePaneState`, `shownFrame`. No module keeps its own shown flag or reads `$.ui.panes()` for it.
- `showPaneState($, panes, spec, state, isCurrent?)` places through `placePane`, then on success notes shown and focus from `$.ui.panes()` and invalidates `ui.render`; it returns `true`, `false` (not placed: state hidden) or `null` (superseded, or `isCurrent` false: state untouched). Settings passes its generation check as `isCurrent`.
- `closePaneState` hides the state and calls `$.ui.close`; module extras (Settings generation, picker drafts, Context `releasePane`) run beside it in the module.
- Every pane `ui.render` starts with `shownFrame($, e, panes, spec, state)`: null when the engine no longer shows the pane (state hidden, the module releases its runtime and answers an empty Box), else it notes shown and `e.props.isFocused` and returns the `framedPane`.
- Press on a strip block keeps each module's own toggle (owner has not decided to unify it): Settings, picker and Limits close a shown pane; Context closes it only when shown and focused, and a shown unfocused Context pane is reopened for the keyboard (closed if it stays unfocused).
- Arrow moves in a pane `ui.scroll` that await engine calls run through one `createMoveGuard()` per pane (Settings, picker, Context arrows): a move arriving while one runs is consumed and dropped.

### Opening (do not regress)

- `$.ui.open` draws at any width only when it ANSWERS the person: the hook of a Button/Input/Select press, a typed slash command, or `prompt.submit`. Anything else waits undrawn below 144 columns (110 for an id opened before). The person often runs ~87 columns.
- `$.ui.open` is the FIRST engine call of that hook, no `await` before it (`$.ui.panes()`, `$.prompt.read()`, `$.clock.sleep()` break it). Not "asked": `prompt.edit`, `prompt.change`, timers, `session.start`, `ui.scroll`, `ui.focus`, anything after an `await`.
- `focus: true` is granted only while the prompt holds the keys over an EMPTY composer; once it is cleared, a second open asks again.
- All opens go through `core/pane/open` `openPane`, with one `createPanes` runtime from the composition root: it calls `$.ui.open` first, then, after successful placement, closes every other pane of this plugin (hidden tabs too): only one HUD pane stays open. Failed placement keeps the previous pane. Generation checks stop superseded openings from closing the latest pane or restoring stale visibility; callers ignore a null result.
- Module opens go through `placePane` (called only by `showPaneState`), which adds the one "pane did not open" toast; reopens (`stepBack`, focus claims) stay silent. A placed pane left without the keyboard (seen on a mouse press of a strip block) asks once more in the background: after `paneConfig.focusRetryMs`, while the pane is still shown, unfocused and no newer open ran, it reopens through `openPane`.
- Focus reclaim on a press (twice regressed): a mouse press in an unfocused pane asks for the keyboard only from `registerPanePress` (`core/pane/hooks`), which, while `Panes.focused` lacks the pane, starts `openPane` BEFORE `next(e)` (no `await`, no `$.ui.panes()`, no press closure first), then lets the press run, then rings the pressed element through `focusElement` (silently denied when the press redrew it away). A press whose closure closes the pane still ends closed. A focused pane passes straight to `next(e)`. Guarded by `tests/pane-focus.test.ts`.

### Closing

- Every `$.ui.open` passes `closeOnEscape: true` (see Engine facts). Normal `ui.close` hooks release the closed module's state, including unapplied picker drafts.
- Escape steps back before it closes, in every pane: every pane's `ui.close` is `registerPaneClose` (`core/pane/hooks`), whose `back()` returns the level to leave as `{ run, focus? }` or null, and which first calls `stepBack`. A `person` close while the pane has a level to leave runs that step, refuses the close (answers without `next`) and reopens through `openPane` with the same args to ask for the keyboard again; at the top level, or on a `plugin` close (strip toggle), the pane closes. The engine cannot tell Escape from the close mark (both `person`), so both step back.
- After a step back's reopen, `registerPaneClose` rings the `focus` key through `focusElement` (Context: the collapsed branch head). `run` takes no `$`: `stepBack` invalidates `ui.render` itself, so Context collapses through the pure `collapseKey`.

### Frame and focus look

- While `Pane.isFocused` is false, `paneUi` grays and dims all Text and removes inverse/bold highlights; focused panes restore colors. Headers are plain bold, no background; `PaneZones.header` defaults to the bold title clipped to the pane width. Settings uses a compact neutral inverse selection, no colored accent.
- Unfocused status: an absolute overlay at the top right of the window, adding no rows: bold warning ` INACTIVE ` (only while it fits `paneConfig.status.labelShare` of the width; narrow panes keep only the shortcut) beside the inverse focus chord (`Panes.keys`, read from the person's keybindings at `session.start`, else the engine's `ctrl+x tab`). Nothing while focused. `abovePrompt:focus` is bound in Chat, where the engine registers that action.
- Navigation help shows only while focused, never repeats focus instructions. Every pane is a `framedPane`: `PaneZones.header` on the first row, `PaneZones.hint` drawn dim on the last row when no `footer` is given, the body between them. The header and the help are real rows of a tree that is never scrolled by the engine, so they cannot move (owner: the heading must never scroll away, and nothing may twitch on a scroll).
- `framedPane` draws `bodyRows + 1` rows (the trailing blank row lets vertical arrows reach `ui.scroll`), so every framed pane must register a `ui.scroll` hook that answers every person scroll without `next` (wheel, arrows, page keys, Home/End): the engine window stays at row 0 and only the body moves, by the pane's own logic. One passed to `next` scrolls the whole tree by a row and the header leaves the window (seen in Limits; Settings passed its page keys until fixed).
- Long content scrolls in the plugin's own window, never the engine's (the cause of the twitching the owner saw on every scroll; do not go back): Context used a tall tree under the engine window with the header and help as absolute rows re-pinned at `scroll.offset` on each draw (`scrolledPane`, removed). The engine moves its window before the next draw, and its own moves (a held element kept in view, a clamp) ask for no draw at all, so the pinned rows lagged a frame behind every scroll. Now the body is a kit `viewport` and a scroll only changes its `first` and redraws.
- Focus moves go through `focusElement`; arrow intent is read only through `scrollIntent` (see pane bindings in Engine facts).

## Strip

- The strip (`SessionMode`) never takes focus. A Button `action` presses it by chord; only validator-accepted actions work (`diff:back`, `diff:nextSource`; `messageSelector:bottom` is refused and kills the render).
- The strip render reads `$.ui.panes()` once per draw and hands the list to `noteSettings`, `notePicker`, `noteLimits` and `contextBlock` (`paneShown` in `core/pane`): it draws every second (`stripTickMs`), and each read is an engine call.
- Blocks are one ordered list (`id`, `label`, optional `gap`/`overlay`/`action`, `isPressable`): that order is the ←/→ order; the chord starts on the first block. Enter acts only on pressable ids.
- The effort block opens no pane: a press (mouse, space or Enter, which takes the newline filler) closes the picker and runs bare `/effort`, the engine's own effort list (owner's choice). The model block works the same way and runs bare `/model`, the engine's own model list (owner's choice "for now": the picker pane code stays, but nothing opens it; restoring it means bringing back `showPicker`/`activatePicker` and the strip routing from git); the 5h and 7d blocks open the Limits pane.
- `⚙` is drawn wider than the one cell the engine counts, so its face is `⚙ ` (trailing space): the hover inverse covers the whole glyph.
- An empty composer raises no `prompt.edit` for ←/→, so nav fills it with a 2-char filler (cursor 1) and consumes the moves. Enter is not an edit: on a closed `ctx`/`5h`/`7d`/`⚙` the filler is two U+2800, Enter submits and `prompt.submit` opens the pane (a cancelled submit always prints "Prompt not submitted"); elsewhere `\` + U+2800, so Enter becomes a silent newline edit. Never move the first open into `prompt.edit`/`prompt.change`.
- After a cancelled submit the engine restores the text (`prompt.change`, origin `engine`): clear it there.
- Hover and selection look the same: inverted face + `overlay` shown. No underline anywhere (owner dislikes it). Context and limit blocks draw an overlay only when their On hover format is set (otherwise hover only inverts); their face is centered in the wider of the shown and hover readings, so hovering never shifts the strip.
- The overlay Box is unkeyed and carries `hover` only while hidden (validator limits below). An overlay over a Button takes the click, so a pressable block's overlay is a Button with the same `onPress`.
- Hints: `cleanHint` removes from each ` · ` part of the engine hint line the match of each hidden hint's pattern (`stripConfig.hints`) and drops parts left empty. Patterns match whole parts, except the parenthetical `(… to cycle)` and `(… to manage)` inside the mode and tasks pills.

## Settings

### Store

- `$.store` key `settings`: `{ activity: { model, effort, context, fiveHour, sevenDay, shells, agents, settings, cache }, display: { model, context, fiveHour, sevenDay, cache: { format, hover, until } }, hints: { <HintKey>: shown } }`. Defaults in `settingsConfig.defaults` (7d off, hover only for the 5h/7d countdown, five hints hidden).
- Parsing defaults each bad field independently; a hover equal to the format is `null` (None). Locked modules (`isLocked`: shells, agents) always parse off.
- Migration: `activity.limits` with `limits.fiveHour`/`sevenDay` become the window flags; `limits.resetTime` becomes the countdown format with the labeled reading on hover. Legacy `activity.limits: false` disables both windows even when the saved `limits` object is incomplete; explicit current window flags still win.
- Display vocabulary is shared only through `core/config` types (`Display`, `ModelFormat`, `ContextFormat`, `LimitFormat`, `CacheFormat`, `CacheDisplay`, `HintKey`): `settingsConfig.displays` holds each format's sample label and hint, modules implement the formats, `stripConfig.hints` holds each hint's pattern.
- Model and effort are one Settings module: Enabled flips `model`; the effort is part of its Format options (`Opus 5.5 high`, `Opus 5.5`, `Opus high`, `Opus`), which flip `activity.effort`; the focused Format note reads `model with effort` on the options that carry it. `isActive` counts effort on only while model is on (no effort-only strip); turning model off releases and forgets the effort too. Each part still removes its own block and picker section; both off: no picker.

### Pane

- Opens from `/aiva-hud` or the `⚙` block at the section list (`settingsConfig.sections`: HUD, Cache timer, Hints), each with a dim description, cut with … where narrow. The descriptions are the original ones the owner chose; no state summary (owner rejected `4 of 5 on` and the like). No General section until Language is built.
- Below the list, after a blank row when there is room, `[ Reset to defaults ]` asks first: its row becomes `Reset all settings to defaults?` with `[ Cancel ]` (focused) and `[ Reset ]` in error color, ←→ between them; the sections stay drawn but inert and out of navigation; Escape or Cancel returns to the Reset button. Reset restores display and hints at once and flips each differing activity flag through the toggle, so released runtimes and closed panes follow as on a manual toggle.
- Star request (the owner chose a quiet row over delays, toasts or reminders): below Reset, after a blank row when there is room, dim `★ Like this mod? Star aiva-hud on GitHub` (★ and `[ Star ]` in warning color, the only accent) with `[ Star ]` `[ Hide ]` beside it (←→ between them, inert while resetting or busy); when the text does not fit beside them the buttons go to a row below, if there is one (before the blank rows), else the text is cut; dropped when the pane has no row for it. Both buttons hide it forever (`$.store` key `star`, outside `settings`, so Reset never brings it back) and move focus to Reset. `Star` tries `gh api --method PUT user/starred/<repo>`, then the system opener, then `$.ui.copy`, and shows the outcome in success color until Settings closes (cleared on the next open). On the first Settings open of a session, an existing star (`gh api user/starred/<repo>` exits 0) hides it silently.
- Entering a section focuses its first control (`focusKey`, Back when it has none); Back or Escape returns to the list with that section selected. ↑↓ walk `settings.navigation` (Back first).
- Settings commits its selected row before awaiting `focusElement`, so windowed rows stay visible even when the engine denies focus; there is no separate pending selection. A completed `showSettings` updates visibility only while its generation is current, so a close or newer navigation wins.
- A section's preview row sits under the header, with a blank row before the controls when they leave room.
- HUD and Cache timer controls are kit `cycle` rows (`fit`, shared label width, always wrapping: settings options are unordered sets) with an optional note beside, or wrapped below when it does not fit. ←/→ step the selected row, a press advances it. Enabled is the exception: a kit `checkbox`, its `Enabled: ` label in the label column like the cycle rows and a bare `[x]` (no checkbox label) where their `‹` starts, space/enter or a click toggles, ←/→ do nothing (owner chose a checkbox for the mouse; the cycle rows stay, and the owner declined split `‹ ›` buttons, inline option chips and module tabs). Owner rejected the unlabeled `[x] Enabled` indented into the value column: with the label column empty it stood out of the `Label: ‹ value ›` rhythm. Not chosen: the checkbox beside the Module carousel (`‹ Context ›  [x] on`), a checkbox list of modules with a per-module format page.
- HUD: Module picks the module, then Enabled (disabled with `in development` for locked ones), Format (when more than one) and On hover (`None` plus the other formats). The preview is plain Text, no Buttons: with keyed preview blocks above the controls, an off module's ghost made the gear look focused (likely the engine ring keeping its position when a stop is inserted before it; unverified). It shows the strip with sample values, all dim but the chosen block, drawn as in the strip (bold, its color, dim `5h`/`7d` prefix, effort in its own color) between `→ ←` arrows, inverse with the hover reading while On hover is focused. An off chosen module stays at its place, dim and struck through, arrows dim too, so turning it off visibly changes the preview.
- Cache timer: Enabled, Format, Until (Shown/Hidden: the dim `(until 14:05)`, or `(since …)` once cold). The preview draws the timer as the cache module does (`cacheGlyph`, bold success countdown, dim until part), dim and struck through while off.
- Hints: a kit `checkbox` list, one row per `HintKey` labeled by its text (`[x]` shown), space/enter toggles, ←/→ do nothing; the header shows `3 hidden` (nothing when all are shown). The preview draws the focused hint as the engine does: dim, after the `⏵⏵ auto mode on` pill (warning color), no arrows, struck through while hidden. The list window scrolls only when the focus leaves it (`settings.first`, reset on entering), never re-centering: a centered window shifted every row under the engine focus ring and the ring landed on a neighbour (seen from the 4th-5th row; cause inferred). A kit `scrollbar` sits at the right edge while the list does not fit.

## Model picker

- Layout: a `tabs` row (active `Latest models`, no stop; `All models…`, a dim action that closes the pane and runs bare `/model`, since the engine gives plugins no full model list), a blank row, the Model and Effort carousels, a blank row, `[ Apply ]` with its status, the error, the mid-session switch note. Short of rows, kit `stack` drops whole rows by priority: model, effort, apply, tabs, error, note, blank rows first.
- Focus stops follow screen order (all models, model, effort, apply) but focus starts on the first carousel; ↑↓ walk `run.stops`, ←/→ step only the selected carousel (model wraps, effort `wrap: false`), a press advances it.
- Colors: Anthropic has no official per-model colors; `modelColors` holds the owner's (fable `#9B59B6`, opus `#D97757`, sonnet `#6A9BCC`, haiku `#E05252`, else theme `claude`), for the picker model value and the strip model name.
- A carousel shows nothing beside it while its draft equals the applied value (owner finds a `current` mark redundant); once changed, dim `current: <applied>`. Labels share one `labelWidth`; both carousels use `fit` (on trial by the owner).
- The model carousel is not a fixed list (owner asked that every latest model show up): its families come from the stored `Model IDs` line, in its order (`familyOf` takes any `claude-<family>-` id), so a new family appears by itself; `pickerConfig.fallbackFamilies` (fable, opus, sonnet, haiku) fills in only while the store knows fewer than two. A family is kept unless the engine `model` row has options and none of them names it. Apply runs `/model <alias>` when the row offers the alias, else the family's latest id (`Choice.command`). A new family gets the fallback color. A session model that is not its family's latest id is an extra first option (value `''`), so an untouched draft never switches.
- Versions come from the system prompt line `Model IDs — Fable 5.1: 'claude-fable-5-1', ...` (`prompt.compose`), saved per family in `$.store` (`models`); `$.session.model()` fills only unknown families. No extra model requests. A family is current when the session model is its latest id.
- The strip effort is the last observed turn effort, else `settings.effortLevel`. A `/effort` run (typed, or the picker's Apply) records its new level at once through a `command.run` hook (`registerEffortCommand`): the typed level unless the output reads as a failure, else the engine `effortLevel` config row, else nothing (falls back to the setting). Before it, the strip kept the previous turn's effort until the next turn (seen: `high` after `/effort medium`). Its matcher is a literal: the validator does not resolve a config constant (`command=?`).
- Effort changed anywhere else (bare `/effort` list from the strip, the engine `/model` picker, `/config`) reaches the strip within `pickerConfig.effortReadMs` (2 s): the effort block reads the engine `effortLevel` row at most that often (`watchEffort`, `Model.effortWatch`, reset on toggle off) and records it only when the row CHANGED since the last read, so a turn effort the engine downgraded is never overwritten by a static row. Owner reported the strip effort out of sync with the console.
- One shared effort draft: last observed turn effort, else `settings.effortLevel`. No effort options: "Effort: not available", no stop.
- Apply runs `/model` only for another model, `/effort` only when the draft was touched and differs or the model changed (`changesOf`); its status shows the diff (`Opus 5.5 → Sonnet 5.5 · high → max`) or "No changes". Apply stays a stop but is dim and inert with no changes, while applying, or while `live.isWorking` (status: "Claude is working. Apply when the turn ends."); drafts stay editable. A model change adds the note that a mid-session switch drops the prompt cache.
- Sequential apply: success closes the pane; a failure keeps it, clears the drafts already applied and shows `Not applied: <message>` in error color (one line, up to two rows) until the next edit or apply. No toast.

## Limits

## Engine facts (2.1.310)

- Only a keyed `Button` gets the pane focus ring (↑↓ and scroll-to-focus skip plain `Text`). A walkable row is a `Button` and a nav node (`isOpen: null` for a leaf). Plain Text keys are stripped from the validated tree: address with keyed Boxes/Buttons.
- Validator: no `hover {display:'flex'}` on a Box already flex; no `hover` on a keyed Box drawn `display:'none'`.
- `closeOnEscape: true` on `$.ui.open`: the engine eats Escape before mod listeners, this turns it into `ui.close` (origin `person`); Escape at an idle empty prompt does the same for an unfocused pane. Escape hands the keyboard back, so a refused close must ask for focus again. A `ui.focus` without an element is not necessarily Escape (close marks, tabs).
- Pane bindings: up/down = `pane:scrollUp`/`pane:scrollDown`, left/right = `pane:top`/`pane:bottom`, space and enter = `abovePrompt:press`. `scrollIntent` is their only reader: a person scroll of the whole tree is left/right, of one row up/down; pointer and plugin scrolls are no arrow. Page keys ask for `bodyRows`, the wheel for its ticks with a `pointer`.
- `ui.scroll` fires before the window moves, at its edges too; a hook that answers without `next` leaves the engine window where it is, which is how a pane scrolls rows of its own under a fixed header (the engine's documented way). A move through `ui.scroll` asks for a draw; the engine's own moves on the terminal (an end followed, a clamp, a held element kept in view) do not. Unverified on the live engine: whether the focus ring follows a Button's `key` or its place among the stops across a redraw; the viewport keeps both steady.
- Keybinding changes (`~/.claude/keybindings.json`) need a session restart. A plugin Button `action` fires from a Global binding; `diff:nextFile` bound in Chat did not fire. `abovePrompt:focus` defaults to ctrl+x tab.
- Missing: `$.model.list`, `$.session.setModel`, `$.settings.write`, `ui.key`, `holdsKeys`. `$.settings` is read only.
- No API opens a URL: `Link` (OSC 8) answers only a mouse click. `$.process.run` (CLI only, no shell, rejects when the command is missing) opens it by `systemOf`: Windows `rundll32 url.dll,FileProtocolHandler <url>`, mac `open`, Linux `xdg-open`. `$.ui.copy` is the fallback on every surface.
- Windows: `rundll32` exits 0 even when nothing opened, and `explorer.exe <url>` exits 1 even when it did, so neither tells the truth; `rundll32` stays (the documented URL handler, no window of its own on a missing handler).
- WSL: `wslview <url>` (wslu, exits 0 only when opened), then `explorer.exe <url>` through interop, where a resolved run counts as opened (its exit code is 1 on success); a rejected run (not found) falls through to copy.
- `$.config.set('model')` also rewrites global `settings.json`: never use it. `/model <alias>` and `/effort <level>` via `$.command.run` change this session only; their output shows in the transcript.
- Breakdown has no per-tool list for plugins and `$.tool.list()` cuts descriptions to 300 chars; tool schemas are not visible at all. A pass-through `tool.describe` hook sees each tool once per session with its deferral (`$.ui.invalidate('tool.describe')` asks again).
- `ToolCallResult.text` joins only text blocks: an image Read reads as nothing there. Its `result` is `{ type: 'image', file: { base64, dimensions: { displayWidth, displayHeight, ... } } }`. A Write `result.type` is `create` or `update`. Read answers `file_unchanged` when the model already holds the file.
- MCP server instructions reach the model only as the `mcp_instructions_delta` attachment (`prompt.attachment`), one `## <server>` block each, sent on session start, clear, compact.
- The `PromptHint` line after the mode pill (`⏵⏵ auto mode on (shift+tab to cycle)`) can carry: `gh auth login for PR status` / `install gh for PR status`, `/tasks to see subagents`, `esc to interrupt`, `ctrl+t to show|hide tasks`, `esc to return to team lead`, `? for shortcuts`, `← N agents`, `ctrl+c to copy` with `shift+click to native select` in the same part, `hold space to speak`, `↓ to manage` / `enter to view tasks` (also `(↓ to manage)` after the tasks pill), `enter to view artifacts` / `enter to open in browser`.
